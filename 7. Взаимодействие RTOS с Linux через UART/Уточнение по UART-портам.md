В процессе работы было выявлено, что в используемом нами OpenTitan из GitHub аппаратно поддерживается несколько физических UART-портов, но в симуляторе Verilator по умолчанию активируется и работает только один из них — uart0, которому на хосте соответствует единственный виртуальный псевдотерминал (например, /dev/pts/3). С точки зрения операционной системы, этот ресурс существует в одном экземпляре, и он может иметь только одного активного владельца, который будет отправлять и принимать данные.

Изначально мы пытались запустить наше FreeRTOS-приложение через ./bazelisk.sh run ... -- --exec=console. Идея была удобной: opentitantool сам захватывает виртуальный UART-порт и становится мостом между клавиатурой пользователя и симулятором. Однако в нашем окружении этот режим не сработал: мы печатали в консоли, но данные не доходили до UART, не было ни эха, ни реакции на нажатие Enter. При этом сам порт /dev/pts/3 существовал и был занят процессом opentitantool, но передачи данных не происходило.

Чтобы обойти эту проблему, мы отказались от использования --exec=console. Вместо этого мы запустили симулятор командой ./bazelisk.sh run ... -- --exec="", при которой opentitantool запускал Verilator, но не пытался захватить управление UART. В этом случае порт /dev/pts/3 создавался, но оставался свободным — у него не было активного процесса-владельца, который бы читал и писал данные. В итоге мы смогли отправлять данные с Linux в симулятор OpenTitan, просто подключившись к свободному виртуальному UART-порту(например через через screen).

Таким образом, ключевой вывод: виртуальный UART-порт симулятора поддерживает только одного активного клиента. Если штатный механизм opentitantool --exec=console в вашем окружении не справляется с передачей данных (захватывает порт, но не обеспечивает ввод-вывод), нужно принудительно запустить симулятор без захвата порта (через --exec="").
