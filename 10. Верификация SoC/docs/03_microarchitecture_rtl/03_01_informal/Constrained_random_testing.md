### МЕТОД: Контролируемо-случайное тестирование (Constrained Random Testing, CRT)
### КАТЕГОРИЯ: 3. Микроархитектурная и RTL-верификация / Неформальная
### ФОРМАЛЬНОСТЬ: полуформальный

### СУТЬ МЕТОДА:
Контролируемо-случайное тестирование (CRT) – это метод верификации цифровых схем, при котором входные тестовые воздействия генерируются случайным образом, но в рамках заданных проектировщиком ограничений (constraints). В отличие от полностью случайного тестирования, где любые входные комбинации равновероятны, CRT позволяет направить генерацию в осмысленные области пространства входов, исключая невалидные или неинтересные комбинации. Это сочетает широту случайного перебора с фокусировкой направленного тестирования.

Суть метода заключается в следующем: инженер описывает среду верификации (testbench), в которой объявляются случайные переменные и накладываются ограничения на их допустимые значения. Симулятор многократно генерирует случайные наборы входных данных, применяет их к верифицируемому устройству (DUT) и проверяет корректность выходов через эталонные модели (reference models) или встроенные проверки (assertions). В случае нарушения ограничений или несовпадения результатов формируется сообщение об ошибке.

CRT особенно эффективен для обнаружения редких граничных условий (corner cases), которые трудно предугадать при ручном написании тестов. Большое количество случайных тестов (сотни и тысячи) позволяет исследовать поведение схемы в самых разных условиях. При этом, в отличие от формальных методов, CRT не требует математического доказательства и работает с любыми схемами, включая сложные процессорные ядра и системы на кристалле (SoC). Данный метод широко применяется в промышленной верификации и является основой методологии Coverage-Driven Verification (CDV).

### ИСТОРИЧЕСКАЯ СПРАВКА:
Метод контролируемо-случайного тестирования стал активно развиваться в конце 1990-х — начале 2000-х годов, с появлением инструментов Specman/e (Verisity, ныне Cadence) и SystemVerilog (IEEE 1800). Specman привнес в практику верификации язык e с мощным механизмом генерации случайных данных и ограничений. Позже SystemVerilog включил аналогичную функциональность через конструкцию `rand`/`randc` и блоки `constraint`. С появлением [cocotb](../../tools_instructions/cocotb.md) в 2010-х годах (Chris Higgs, Potential Ventures) метод стал доступен в экосистеме Python с открытым исходным кодом. Ключевые работы: Bergeron, "Writing Testbenches: Functional Verification of HDL Models" (2000); IEEE Std 1800-2023 (SystemVerilog).

### ПОДРОБНОЕ ОПИСАНИЕ МЕТОДА И ЭКСПЕРИМЕНТА:
Продемонстрируем данный подход на простом 4-битном сумматоре, описанном на Verilog:

```systemverilog
module adder (
   input  [3:0] a,
   input  [3:0] b,
   output [4:0] sum
);
   assign sum = a + b;
endmodule
```

Для него напишем cocotb-тестбенч на Python. Тестбенч генерирует 100 случайных пар входных значений a и b в диапазоне [0, 15] (ограничение в 4 бит). Каждое значение подаётся на входы модуля adder через `.value =`, после чего ожидается 1 нс (Timer(1, unit="ns")) для стабилизации логики. Затем фактическое значение суммы считывается с выхода и сравнивается с эталонным `a + b`. Если все 100 тестов проходят, выводится сообщение об успехе.
Выбран cocotb, так как он предоставляет простой Python-интерфейс для верификации HDL-моделей, не требуя глубокого знания Verilog/SystemVerilog для написания тестов. Симулятор – [Icarus Verilog](../../tools_instructions/iverilog.md) 12.0. Запуск через Makefile.cocotb и run.sh.

```python
import random
import cocotb
from cocotb.triggers import Timer

@cocotb.test()
async def test_adder_constrained_random(dut):
   random.seed(42)
   for i in range(100):
       a = random.randint(0, 15)
       b = random.randint(0, 15)
       dut.a.value = a
       dut.b.value = b
       await Timer(1, unit="ns")
       expected = a + b
       actual = int(dut.sum.value)
       assert actual == expected, f"FAIL: a={a} b={b} expected={expected} got={actual}"
   dut._log.info("All 100 constrained-random tests passed!")
```

### ВЫВОД ПО МЕТОДУ:
CRT является одним из базовых и наиболее практически ценных методов функциональной верификации. Он применим для любых цифровых схем – от простых сумматоров до многомиллионных процессорных ядер. Сложность реализации низкая: достаточно иметь тестбенч с генератором случайных стимулов и эталонную модель. Ресурсные затраты линейно растут с количеством тестов и сложностью DUT. Для промышленных процессоров CRT – обязательный элемент верификационного плана, используемый на всех этапах разработки RTL.
