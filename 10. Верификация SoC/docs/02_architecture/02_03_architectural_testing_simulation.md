### МЕТОД: Архитектурное тестирование симуляцией
### КАТЕГОРИЯ: 2. Архитектурная верификация
### ФОРМАЛЬНОСТЬ: неформальный

### СУТЬ МЕТОДА:

Данный метод решает задачу практической проверки соответствия реализации процессора (RTL-модели, симулятора, FPGA-прототипа) эталонной спецификации системы команд. В отличие от формальной верификации, которая требует математической формулировки свойств, архитектурное тестирование заключается в прогоне реальных тестовых программ и сравнении результатов с эталоном. Это самый распространённый и интуитивно понятный метод верификации, применимый на всех этапах разработки.

На высоком уровне метод работает как сравнение двух моделей: тестируемый объект (RTL-модель, симулятор или реальный чип) и эталонная модель (обычно ISA-симулятор, такой как [Spike](../tools_instructions/spike.md) для RISC-V) одновременно выполняют одну и ту же тестовую программу. Результаты выполнения – значения регистров, состояние памяти, исключения, флаги – сравниваются. Если результаты совпадают, тест считается пройденным. Если расходятся, это указывает на ошибку в тестируемой реализации (или, реже, в эталоне), и инженер может проанализировать точку расхождения для локализации дефекта.

Входными данными являются тестовая программа (на ассемблере RISC-V или машинном коде), эталонный симулятор (Spike, Sail) и тестируемая реализация (RTL-симулятор, другой ISA-симулятор или аппаратный прототип). Выходными данными – заключение о прохождении теста (PASS/FAIL) и, в случае неудачи, детальный лог выполнения с указанием инструкции, на которой произошло расхождение.

Метод применяется на всех этапах разработки процессора, начиная с верификации ISA-симулятора и заканчивая приемочными испытаниями кремния. Для RISC-V архитектурные тесты (riscv-arch-test) разрабатываются RISC-V International и являются официальным набором для проверки соответствия ISA. Сильные стороны: метод прост в реализации, не требует специальных инструментов (достаточно симулятора и компилятора), легко автоматизируется, воспроизводим. Слабые стороны: покрытие ограничено написанными тестами (невозможно проверить все комбинации), симуляция эталонной модели может быть медленной для больших тестов, требуется поддержание эталонной модели в актуальном состоянии.

### ИСТОРИЧЕСКАЯ СПРАВКА:

Архитектурные тесты являются неотъемлемой частью верификации процессоров с самого начала индустрии. Для RISC-V архитектурные тесты (riscv-arch-test) разрабатываются RISC-V International и служат официальным набором для проверки соответствия ISA. [Spike](../tools_instructions/spike.md) (также известный как riscv-isa-sim) – эталонный симулятор RISC-V с открытым исходным кодом, разработанный в UC Berkeley в рамках проекта Berkeley Architecture Research. Он широко используется для отладки ПО, верификации и как "золотая модель" при разработке процессоров.

### ПОДРОБНОЕ ОПИСАНИЕ:

Рассмотрим данный метода на практическом примере. Используем [Spike](../tools_instructions/spike.md) (RISC-V ISA Simulator) и кросс-компилятор [riscv64-linux-gnu-gcc](../tools_instructions/riscv-gcc.md). Выполним следующие шаги:

1. Напишем минимальный тест на ассемблере RISC-V (test_sum.s), вычисляющий сумму целых чисел от 1 до 10.
2. Скомпилируем его в ELF-файл с флагами -nostdlib -nostartfiles.
3. Полученный ELF-файл запустим на симуляторе Spike с флагом -l (лог инструкций) в режиме RV64IMAFDC.
4. Spike выполнит каждую инструкцию потактово, формируя детальный лог с адресом, машинным кодом и дизассемблированным мнемоническим представлением.
5. Для корректного завершения без Proxy Kernel (pk) используем механизм HTIF (Host-Target Interface): тест записывает код возврата в ячейку памяти tohost, после чего Spike интерпретирует это как сигнал завершения и выводит *** FAILED *** (tohost = <код_возврата>).

Тестовая программа на ассемблере:

```asm
.option nopic
.section .data
.align 3
.globl tohost
tohost:
   .dword 0
.globl fromhost
fromhost:
   .dword 0


.section .text
.globl _start
_start:
   li t0, 1
   li t1, 0
loop:
   add t1, t1, t0
   addi t0, t0, 1
   li t2, 11
   blt t0, t2, loop
   mv a0, t1
   la t2, tohost
   slli t1, t1, 1
   addi t1, t1, 1
   sd t1, 0(t2)
ebreak
```

Скрипт запуска:

```bash
#!/bin/bash
set -e
DIR="$(cd "$(dirname "$0")" && pwd)"
PROJ="$(cd "$DIR/../.." && pwd)"


ASM="$DIR/test_sum.s"
ELF="$DIR/test_sum.elf"
LOG="$DIR/output.log"


echo "=== Compiling RISC-V assembly ==="
riscv64-linux-gnu-gcc -nostdlib -nostartfiles -fno-pic -Wl,-no-pie \
   -Wl,-Ttext-segment=0x80000000 -Wl,-e,_start \
   -o "$ELF" "$ASM"
echo "Compiled: $ELF"


echo ""
echo "=== Running Spike (ISA simulator) with instruction log ==="
"$PROJ/tools/bin/spike" -l --isa=RV64IMAFDC "$ELF" 2>&1 | tee "$LOG"


echo ""
echo "=== Test result ==="
RESULT=$(grep "tohost" "$LOG" | grep -oP 'tohost = \K\d+')
echo "Sum 1..10 = $RESULT (expected: 55)"
if [ "$RESULT" = "55" ]; then
   echo "TEST PASSED"
else
   echo "TEST FAILED"
   exit 1
fi
```

Ожидаемый результат: sum(1..10) = 55 (0x37). Вывод tohost = 55 подтверждает корректность выполнения тестовой программы. Приводить здесь полный вывод будет излишним.

### ВЫВОД ПО МЕТОДУ:

Архитектурное тестирование симуляцией — обязательный и высокоэффективный метод верификации процессоров. Spike (или аналогичный ISA-симулятор) используется как "золотая модель" на всех этапах разработки RISC-V процессоров. Метод прост в реализации, не требует дорогостоящего оборудования, легко автоматизируется в CI/CD. Ограничения: симуляция в Spike на несколько порядков медленнее реального выполнения на FPGA или в RTL-симуляторе, поэтому для больших тестов (загрузка ОС) применяют ускоренные методы (QEMU, FPGA). Тем не менее, для архитектурных тестов и регрессионного тестирования отдельных инструкций Spike является стандартом де-факто.
