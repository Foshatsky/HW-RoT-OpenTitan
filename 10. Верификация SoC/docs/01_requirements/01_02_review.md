### МЕТОД: Рецензирование (code review)
### КАТЕГОРИЯ: 1. Верификация требований
### ФОРМАЛЬНОСТЬ: неформальный

### СУТЬ МЕТОДА:

Этот метод хотя бы понаслышке знает любой человек, работающий в ИТ. Он решает задачу выявления дефектов в спецификации, RTL-коде и тестах путем экспертной проверки человеком или группой инженеров. Несмотря на развитие автоматических методов верификации, человеческая экспертиза остаётся одним из наиболее эффективных способов обнаружения ошибок – рецензирование выявляет значительную долю дефектов, включая те, которые пропускают линтеры и формальные инструменты.

На высоком уровне метод организуется как структурированный процесс: автор материала рассылает его рецензентам, которые изучают код или спецификацию по формальному чек-листу, фиксируя все найденные несоответствия, нарушения стандартов и потенциальные проблемы. Затем проводится встреча для обсуждения найденных замечаний, после чего автор устраняет дефекты, а рецензенты подтверждают исправления. В процессорной разработке рецензирование обязательно для критических модулей, изменений в архитектуре и расширений ISA.

Входными данными являются исходный код (Verilog, SystemVerilog, VHDL), спецификация или тестовое окружение. Выходными данными – список найденных дефектов с классификацией по уровню серьезности (критические, средние, низкие), рекомендации по исправлению и итоговое заключение о готовности материала к следующему этапу. Чек-лист рецензирования обычно включает проверку полноты спецификации, соблюдения стандартов кодирования, правильности обработки сброса и инициализации, защиту от недопустимых состояний.

Метод применяется на всех этапах разработки процессора, начиная с верификации требований и заканчивая приемочными испытаниями. В RISC-V сообществе рецензирование обязательно для любых изменений в привилегированной архитектуре и официальных расширениях ISA. Сильные стороны: не требует инструментов и лицензий, обнаруживает широкий класс дефектов, передаёт знания между инженерами. Слабые стороны: зависит от квалификации и внимательности рецензента, трудоемок (требует человеко-часов), не даёт формальных гарантий полноты проверки.

### ИСТОРИЧЕСКАЯ СПРАВКА:

Формализовано Fagan (1976) в IBM как "code inspection". Метод Fagan включает: планирование, обзор, подготовку, встречу, доработку, контроль. В Intel/HW-разработке – "RTL review" с чек-листами на 50+ пунктов. В RISC-V сообществе – обязательное ревью перед принятием изменений в ISA.

### ПОДРОБНОЕ ОПИСАНИЕ МЕТОДА И ЭКСПЕРИМЕНТА:

Рассмотрим пример code review на этапе разработки RTL-кода (это более наглядно, чем на этапе разработки требований). Допустим, у нас есть следующий файл с кодом модуля на языке Verilog:

```systemverilog
module regfile #(
   parameter DATA_WIDTH = 32,
   parameter ADDR_WIDTH = 5
) (
   input  wire                  clk,
   input  wire                  rst_n,
   // Read port 1
   input  wire [ADDR_WIDTH-1:0] raddr1,
   output reg  [DATA_WIDTH-1:0] rdata1,
   // Read port 2
   input  wire [ADDR_WIDTH-1:0] raddr2,
   output reg  [DATA_WIDTH-1:0] rdata2,
   // Read port 3 – BUG: missing from spec
   // Write port
   input  wire                  we,
   input  wire [ADDR_WIDTH-1:0] waddr,
   input  wire [DATA_WIDTH-1:0] wdata
);

   reg [DATA_WIDTH-1:0] regs [0:2**ADDR_WIDTH-1];

   // BUG 3: no reset for regs array
   // BUG 4: no enable/we gating on write

   integer i;
   always @(posedge clk or negedge rst_n) begin
       if (!rst_n) begin
           for (i = 0; i < 2**ADDR_WIDTH; i = i + 1) begin
               // Missing: regs[i] <= 0;
           end
       end else begin
           // BUG 1: should skip x0 (regs[0] must stay 0)
           regs[waddr] <= wdata;
       end
   end

   // Read port 1
   always @(*) begin
       rdata1 = regs[raddr1];
   end

   // BUG 2: read port 2 is a copy of port 1 (should be separate)
   always @(*) begin
       rdata2 = regs[raddr2];
   end

endmodule
```

Этот модуль на Verilog – регистровый файл (register file), типичный компонент процессорных ядер. Он хранит набор регистров, позволяя одновременно читать два из них и записывать один по тактовому сигналу.

Комментариями в коде отмечены места с ошибками. В таком случае code review мог бы выглядеть примерно так:

```
Контрольный список проверки:
1. Полнота спецификации
   * Все интерфейсы задокументированы?
   * Параметры описаны?
   * Временная диаграмма присутствует?
2. Стандарты кодирования RTL
   * Нет непреднамеренных защелок?
   * Все выходы назначены во всех ветвях?
   * Разумные списки чувствительности?
3. Специфика RISC-V
   * Регистр x0 (нулевой) никогда не записывается?
   * Регистровый файл имеет 2 порта чтения (RS1, RS2) + 1 порт записи (RD)?
   * Асинхронное чтение, синхронная запись?
4. Сброс и инициализация
   * Все регистры имеют допустимое состояние после сброса?
   * x0 инициализирован нулем?
5. Потенциальные ошибки
   * Сигнал разрешения записи используется правильно?
   * Проверяются границы адреса?
   * Нет комбинационных петель?

**Замечания по обзору:**

Файл: ... (модуль regfile)
Рецензент: ...
Дата: ...

**Ошибка 1: регистр x0 не защищён от записи**
Важность: Критическая
Расположение: regs[waddr] <= wdata;
Описание: Архитектура RISC-V требует, чтобы регистр x0 всегда читался как 0, а запись в него не имела эффекта. В данной реализации запись в x0 происходит как в любой другой регистр, что может нарушить работу программ, полагающихся на то, что x0 равен 0.
Исправление: if (waddr != 0) regs[waddr] <= wdata;

**Ошибка 2: порт чтения 2 является копией порта 1**
Важность: Низкая (неполная спецификация)
Расположение: логика порта чтения 2 (идентична порту 1)
Описание: В спецификации упомянут "порт чтения 2" с отдельными входами raddr2 / rdata2, но реализация идентична порту 1. В комментариях указан "порт чтения 3", который полностью отсутствует.
Исправление: Удалить порт 2, если он не нужен, либо реализовать его с отдельным путём чтения.

**Ошибка 3: отсутствие сброса для массива регистров**
Важность: Средняя
Расположение: блок сброса (пуст)
Описание: Предложение reset в always-блоке не инициализирует массив регистров. Хотя некоторые проекты полагаются на инициализацию FPGA, для ASIC-проектов требуется явный сброс. В частности, x0 после сброса должен быть равен 0.
Исправление: Добавить regs[i] <= 0; в блок сброса.

**Ошибка 4: сигнал разрешения записи не используется**
Важность: Низкая (выбор проектирования)
Расположение: always @(posedge clk or negedge rst_n)
Описание: Вход we (write enable) объявлен, но нигде не используется. Запись происходит по каждому фронту тактового сигнала независимо от we. Это означает, что операция только чтения может случайно повредить состояние регистров, если изменятся адреса или данные.
Исправление: Обернуть запись в условие if (we).

**Итог:**
* Найдено ошибок: 4
* Критических: 1 (защита x0)
* Средних: 1 (отсутствие сброса)
* Низких: 2 (неполная спецификация портов, неиспользуемый we)
* Вердикт обзора: НЕ ПРОЙДЕН – требуется исправление перед выпуском кристалла
```

### ЗАПУСК И ВЫВОД:

Эксперимент не требует запуска инструментов — это имитация человеческого ревью. Вывод представлен в виде списка найденных дефектов выше.

### АНАЛИЗ РЕЗУЛЬТАТОВ:

Найдено 4 дефекта:
1. Критический: запись в x0 не блокируется (нарушение ISA RISC-V).
2. Средний: отсутствует инициализация регистров при сбросе.
3. Низкий: порт чтения 2 — дубликат порта 1 (избыточность/ошибка).
4. Низкий: write enable (we) не используется — запись происходит на каждом такте.

Эксперимент показывает, что код-ревью эффективно находит дефекты разных уровней серьёзности — от нарушений стандартов до критических несоответствий спецификации.

### ВЫВОД ПО МЕТОДУ:

Рецензирование — обязательный этап верификации любого серьёзного процессорного проекта. Метод прост, не требует инструментов, но зависит от квалификации рецензента. Рекомендуется комбинировать с автоматическими методами (линтеры, формальная верификация). В процессорах RISC-V ревью обязательно для изменений в привилегированной архитектуре и расширениях ISA.
